# План задач на спринт: MVP TON Testnet Wallet

## Контекст проекта
Self-custodial криптокошелёк для TON testnet — одностраничное веб-приложение (SPA) на React 18 + TypeScript, работающее полностью на клиенте без собственного backend. Архитектура модульная: крипто-слой (шифрование мнемоники), сервисный слой (взаимодействие с TON testnet через `@ton/ton` SDK), слой состояния (Zustand), слой валидации (pipeline проверок при отправке), UI-слой (экраны и компоненты). Все секретные данные шифруются AES-256-GCM, ключ деривируется через Argon2id (PBKDF2 как fallback). Хранение — localStorage.

## Цель спринта
Реализация полнофункционального MVP кошелька: создание и импорт кошелька по мнемонике, просмотр баланса и истории транзакций с поиском и фильтрацией, отправка и получение TON на testnet с полным pipeline валидации (включая защиту от подмены адреса), экспорт мнемоники, смена пароля, unlock-flow. Опциональные функции (импорт/экспорт по приватному ключу, удаление кошелька) вынесены в следующий спринт. Юнит-тесты обязательны, автоматизированные E2E-тесты желательны. Деплой не входит в скоуп.

#### 3.1 Модуль KDF (Key Derivation Function)

**Статус:** DONE

**Тип:** доменная логика / безопасность

**Описание:**
Реализовать модуль `src/crypto/kdf.ts`, который деривирует 256-битный ключ шифрования из пользовательского пароля через Argon2id (primary) с автоматическим fallback на PBKDF2 при недоступности WASM. Модуль должен генерировать salt, определять доступный KDF-алгоритм и возвращать деривированный ключ вместе с метаданными KDF.

**Контекст и исходные материалы:**
- Документация: раздел 4.1 «Схема шифрования», раздел 4.2 «Формат зашифрованного хранилища», раздел 4.3 «Параметры KDF».

**Зависимости:** зависит от `1.1`

**Шаги выполнения:**
- [ ] Шаг 1: Определить типы в `src/crypto/types.ts`: `KdfAlgorithm` (`'argon2id' | 'pbkdf2'`), `KdfParams` (salt, memory, iterations, parallelism, hash), `KdfResult` (key: Uint8Array, algorithm: KdfAlgorithm, params: KdfParams).
- [ ] Шаг 2: Реализовать функцию генерации 16-байтового случайного salt через `crypto.getRandomValues()`.
- [ ] Шаг 3: Реализовать Argon2id-деривацию: memory=65536 (64MB), iterations=3, parallelism=1, output=256 bit, используя `argon2-browser`.
- [ ] Шаг 4: Реализовать PBKDF2-деривацию через Web Crypto API: iterations=600000, hash=SHA-256, output=256 bit.
- [ ] Шаг 5: Реализовать функцию определения доступности WASM (проверка поддержки Argon2) с кешированием результата.
- [ ] Шаг 6: Реализовать основную функцию `deriveKey(password: string, salt?: Uint8Array): Promise<KdfResult>`, которая выбирает алгоритм автоматически.
- [ ] Шаг 7: Реализовать функцию `deriveKeyWithParams(password: string, params: KdfParams): Promise<Uint8Array>` для повторной деривации при расшифровке (используя сохранённые параметры).
- [ ] Шаг 8: Написать юнит-тесты: корректность деривации (одинаковый пароль + salt = одинаковый ключ), различие при разных паролях, fallback на PBKDF2 при мокнутом недоступном WASM, корректность длины ключа (32 байта).

**Ожидаемый результат:**
Модуль `kdf.ts`, который деривирует 256-битный ключ из пароля, автоматически определяя доступный алгоритм, и модуль `types.ts` с типами крипто-слоя.

**Критерии проверки:**
- Юнит-тесты проходят: деривация Argon2id корректна, PBKDF2 корректна, fallback работает.
- Одинаковые пароль + salt дают одинаковый ключ.
- Разные пароли дают разные ключи.
- Ключ всегда ровно 32 байта.

**Допущения и риски:**
- Риск: `argon2-browser` требует WASM, который может не загрузиться в некоторых окружениях (CSP, старые браузеры). Fallback на PBKDF2 митигирует этот риск.
- Риск: Argon2 с memory=64MB может вызвать проблемы на устройствах с малым объёмом RAM. Для testnet-кошелька это допустимо.

Реализовать автоматизированные end-to-end тесты основных user flows на реальном testnet. Использовать Playwright или Cypress.

**Контекст и исходные материалы:**
- Документация: раздел 12 Фаза 6 (End-to-end тестирование на testnet).

**Зависимости:** зависит от всех предыдущих задач

**Шаги выполнения:**
- [ ] Шаг 1: Установить и настроить Playwright (или Cypress).
- [ ] Шаг 2: Тест: создание нового кошелька (Welcome → Create → Password → Backup → Main). Проверить: Main Screen отображается, адрес присутствует, баланс = 0.
- [ ] Шаг 3: Тест: импорт кошелька по заранее подготовленной мнемонике (с известным балансом на testnet). Проверить: баланс отображается, транзакции загружаются.
- [ ] Шаг 4: Тест: отправка TX (если есть баланс): заполнение формы → валидация → подтверждение → результат.
- [ ] Шаг 5: Тест: receive screen — QR-код рендерится, адрес копируется.
- [ ] Шаг 6: Тест: export мнемоники — ввод пароля → показ слов → автоскрытие.
- [ ] Шаг 7: Тест: unlock flow — закрыть/перезагрузить → unlock modal → ввод пароля → Main.

**Ожидаемый результат:**
Автоматизированные E2E-тесты покрывающие основные user flows.

**Критерии проверки:**
- Тесты запускаются через `npm run test:e2e`.
- Создание кошелька проходит полностью.
- Импорт с testnet-мнемоникой показывает баланс.
- Все тесты проходят (при доступном testnet API).

**Допущения и риски:**
- Риск: testnet API может быть нестабилен, что приведёт к flaky E2E тестам. Митигация: retry в тестах, tolerance к таймаутам.
- Риск: для теста отправки нужен testnet-кошелёк с балансом. Необходимо предварительно получить тестовые TON через faucet.
- Допущение: E2E-тесты — «желательно». Если время ограничено, приоритет отдаётся юнит-тестам (задачи 11.1, 11.2).
